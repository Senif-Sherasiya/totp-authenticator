# Building a New App That Accepts Codes From the Authenticator

Audience: a developer building (or retrofitting) one of the owner's published apps so that it unlocks free access when the user enters a code generated by this authenticator.

Read `AUTHENTICATOR.md` first for the generator side. This document covers only what the **verifier** inside your app must do so that its result always agrees with the authenticator.

---

## 1. The agreement between the two sides

The authenticator and your app share exactly three things. If any differ, codes will never match.

| Shared item | Value |
|---|---|
| Secret | The same Base32 string, configured on both sides |
| Digits | 6 by default (6–8 allowed per app) |
| Period | 30 seconds by default (15–60 allowed per app) |

Fixed for everyone: **HMAC-SHA1**, Unix time in **UTC**, RFC 6238 / RFC 4226.

There is no network call. Both sides compute the same code independently from the secret and the current time.

---

## 2. What your app must implement

1. Hold the secret (see section 5 on where and the security limits).
2. Compute the expected code for steps `current-1`, `current`, `current+1`.
3. Compare the user's input in constant time.
4. **Accept a step only once.** Remember the last accepted step and reject any step less than or equal to it.
5. On success, unlock access and persist both the unlock and the last accepted step.
6. Limit wrong attempts (see section 6).

The authenticator displays only the current step's code. The ±1 window exists so a slightly slow typist or a small clock difference still works.

## 3. Easiest and safest route: reuse the same Dart file

If your app is Flutter/Dart, **copy `lib/core/otp/totp.dart` from this project unchanged** into your app. It is pure Dart and depends only on `crypto`. Using the identical file guarantees the same algorithm, Base32 handling and time maths.

Add to your `pubspec.yaml`:

```yaml
dependencies:
  crypto: ^3.0.7
  flutter_secure_storage: ^11.2.0   # to persist the last accepted step / unlock flag
```

Then add this verifier (tested against the RFC 6238 vector at t=59, replay, ±1 step skew and 2-step rejection):

```dart
import 'dart:typed_data';

import 'totp.dart'; // the file copied from the authenticator

class TotpVerifier {
  TotpVerifier({
    required String secretBase32,
    this.digits = 6,
    this.periodSeconds = 30,
    this.window = 1,
  }) : _key = Totp.decodeBase32(secretBase32);

  final Uint8List _key;
  final int digits;
  final int periodSeconds;
  final int window;

  /// Returns the matched step counter, or null if the code is wrong, expired,
  /// or already used. The caller MUST persist the returned step as the new
  /// lastAcceptedStep when it is non-null.
  int? matchStep(String input, DateTime now, {int? lastAcceptedStep}) {
    final code = input.replaceAll(RegExp(r'\s'), ''); // allow "123 456"
    if (code.length != digits) return null;

    final current = Totp.counterFor(now, periodSeconds: periodSeconds);
    int? found;
    for (var step = current - window; step <= current + window; step++) {
      final expected = Totp.hotp(_key, step, digits: digits);
      // Check every step (no early exit) so timing does not reveal which matched.
      if (_constantTimeEquals(expected, code) &&
          found == null &&
          (lastAcceptedStep == null || step > lastAcceptedStep)) {
        found = step;
      }
    }
    return found;
  }

  static bool _constantTimeEquals(String a, String b) {
    if (a.length != b.length) return false;
    var diff = 0;
    for (var i = 0; i < a.length; i++) {
      diff |= a.codeUnitAt(i) ^ b.codeUnitAt(i);
    }
    return diff == 0;
  }
}
```

Usage:

```dart
final verifier = TotpVerifier(secretBase32: kSecret); // digits/period if non-default

Future<bool> tryUnlock(String input) async {
  final last = await storage.readLastStep();               // int? from secure storage
  final step = verifier.matchStep(input, DateTime.now(), lastAcceptedStep: last);
  if (step == null) return false;
  await storage.writeLastStep(step);                       // persist BEFORE unlocking
  await storage.writeUnlocked(true);
  return true;
}
```

Notes:
- `DateTime.now()` is fine: `Totp.counterFor` uses `millisecondsSinceEpoch`, so the device time zone does not matter.
- Persist `lastAcceptedStep` **before** granting access, so a crash cannot allow a replay.
- The window is `current-1 … current+1`. With the "greater than last accepted" rule, a code from a future step (+1) used early makes the current step's code unusable afterwards. That is consistent with the one-time rule and expected.

## 4. If your app is not Dart (Kotlin / Java / Swift / JS)

Reimplement exactly these steps. Do not substitute a library without checking it against the test vectors below.

```
secretBytes = base32Decode(secret)          // RFC 4648; ignore spaces, '-', '=' ; case-insensitive
counter     = floor(unixSecondsUTC / period)
msg         = 8-byte big-endian(counter)
hash        = HMAC_SHA1(key = secretBytes, msg)          // 20 bytes
offset      = hash[19] & 0x0f
binary      = ((hash[offset]   & 0x7f) << 24)
            | ((hash[offset+1] & 0xff) << 16)
            | ((hash[offset+2] & 0xff) <<  8)
            |  (hash[offset+3] & 0xff)
code        = zeroPad(binary mod 10^digits, digits)
```

Common mistakes that make codes never match:

| Mistake | Effect |
|---|---|
| Using the Base32 **text** as the HMAC key | Totally different codes. Decode first. |
| Using local time or a time-zone-adjusted time | Codes differ by hours of steps. Use epoch seconds. |
| Counter as little-endian or as text | Wrong codes. Must be 8 bytes, big-endian. |
| Not zero-padding | Codes starting with 0 (e.g. `070818`) fail. |
| Different digits or period than the authenticator | Never matches. |
| SHA-256/512 instead of SHA-1 | Never matches. |
| Treating the signed Java `byte` incorrectly | Mask with `& 0xff` / `& 0x7f` exactly as above. |

## 5. Where the secret lives, and an honest security note

The secret has to exist inside your app so it can verify offline. Consequences:

- Anyone who can extract the secret from your APK (decompiling, memory inspection) can generate valid codes for **every user**. This design is a deterrent against casual sharing, not strong protection against a determined attacker.
- Do not hard-code the secret as a plain string literal. At minimum obfuscate the build (`flutter build apk --obfuscate --split-debug-info=...`) and keep the secret out of obvious places such as `strings.xml` or constants named `secret`.
- Use a **different secret for every app** so one leak does not expose the others.
- Do not log the secret or codes, and do not send them anywhere.
- If a secret leaks, rotate it: generate a new one, update the authenticator (Edit → replace secret) and ship an app update. Old secrets in already-installed apps keep working until those apps update, so decide how you will retire them.

Random secret generation:

```
python3 -c "import secrets,base64;print(base64.b32encode(secrets.token_bytes(20)).decode())"
```

## 6. Attempt limiting and unlock persistence

Six digits is only 1,000,000 possibilities, and the window accepts 3 of them. Without limits, guessing is feasible.

Recommended:
- Count consecutive failures; after about 5, lock input for an increasing delay (30 s, 1 min, 5 min…).
- Persist the failure count and lock time so restarting the app does not reset them.
- Consider the clock too: if the user moves the device clock backwards to reuse an old step, the `step > lastAcceptedStep` rule already rejects it. Keep that rule.

Decide what "unlock" means and store it:
- Persist the unlock flag (secure storage), keyed to this install.
- Decide whether unlock is permanent, time-limited or per-feature, and whether a new code is required to renew. This document does not prescribe it; the codes only prove the owner handed one out.

## 7. Adding the new app to the authenticator

1. Generate a new random secret (section 5).
2. Put it into the new app's verifier.
3. In the authenticator: **Add app** → name it → enter the same secret. Leave digits 6 and period 30 unless the new app uses other values (set both sides the same).
4. Alternatively, build an `otpauth://` link and make a QR (see `AUTHENTICATOR.md` section 5) and scan it.

## 8. Test checklist for the new app

Automated (unit tests in the new app):
- Reproduce the RFC 6238 vectors with secret `GEZDGNBVGY3TQOJQGEZDGNBVGY3TQOJQ` (Base32 of ASCII `12345678901234567890`), 8 digits:

| Unix time | Code |
|---|---|
| 59 | 94287082 |
| 1111111109 | 07081804 |
| 1111111111 | 14050471 |
| 1234567890 | 89005924 |
| 2000000000 | 69279037 |
| 20000000000 | 65353130 |

  (6-digit codes are the last 6 digits.)
- Code from the current step: accepted.
- Same code again: rejected.
- Code from step −1 and +1: accepted (if not previously used); step ±2: rejected.
- Spaces in input (`123 456`) handled.
- Wrong length / non-numeric: rejected without throwing.
- Failure counter locks after the limit.

Manual, end to end with the real authenticator:
1. Add the app in the authenticator with the same secret.
2. Enter the displayed code in the new app → unlocked.
3. Enter the same code again → rejected.
4. Wait for the next step, enter the new code → accepted.
5. Turn off automatic time and shift the phone clock by 2 minutes → rejected.
6. Force-close and reopen the new app, retry the old code → still rejected (the last accepted step persisted).

## 9. Quick reference

| Item | Value |
|---|---|
| Algorithm | HMAC-SHA1, RFC 6238 / 4226 |
| Key | Base32-**decoded** secret bytes |
| Time | Unix seconds, UTC |
| Counter | `floor(unixSeconds / period)`, 8 bytes big-endian |
| Defaults | 6 digits, 30 s |
| Verifier window | current step ±1 |
| Replay rule | accept a step only if it is greater than the last accepted step |
| Compare | constant time |
| Secret | random, ≥16 chars (32 recommended), unique per app |
